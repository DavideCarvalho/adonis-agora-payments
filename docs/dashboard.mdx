import { Callout } from 'fumadocs-ui/components/callout';

The dashboard mounts a billing console into your app: a React single-page app plus the JSON API it
runs on. It is built for **daily management** — someone opening it in the morning to ask *is money
coming in, what needs my attention, which customer is stuck, and can I fix it from here* — not for
debugging a single gateway call. Raw payloads, signature traces and timings belong in
[`@adonis-agora/telescope`](/docs/payments/diagnostics); you will not find them here.

Every screen reads through the [billing store](/docs/payments/billing), so it answers instantly and
shows exactly what your database recorded. Only one action leaves your app at all: a refund calls
the gateway that took the payment. A webhook retry re-runs your own handlers, and resolving a
dispute writes a local row and sends nothing anywhere.

```sh
node ace configure @adonis-agora/payments
```

`configure` registers `@adonis-agora/payments/dashboard_provider` in `adonisrc.ts` and publishes
`config/payments_dashboard.ts`. The provider registers the routes on boot — nothing else to wire,
and no extra package to install.

<Callout title="It mounts at /payments, next to the machine endpoints">
The dashboard shares its prefix with `POST /payments/webhook/:provider` and
`GET /payments/client/status`, and that is safe for exactly one reason: **every route the provider
registers is an exact path** — `/payments`, `/payments/assets/:file` and `/payments/api/…`. There is no SPA catch-all, so the dashboard's authorization guard can never end up in
front of a gateway's delivery endpoint.

If you fork this and add a wildcard for client-side routing, the webhook route is what it swallows.
A webhook answering `403` to Stripe looks exactly like a gateway outage from the outside, and you
find out by reading someone else's retry logs. A test in the package asserts no route here contains
a wildcard, for that reason.
</Callout>

## What it shows

The sidebar groups the screens: **Monitor** (Overview, Activity), **Billing** (Payments,
Subscriptions, Customers, Disputes) and **Integrations** (Webhook events). On a phone it becomes a
drawer behind the menu button. The topbar carries the page title, the organization picker (with
[organizations](#organizations) on) and the <kbd>⌘K</kbd> search. The footer shows who is signed
in, a light/dark toggle and a sign-out button. The theme is remembered per browser.

| Screen | Reads | What it answers |
| --- | --- | --- |
| **Overview** | `billingHealth` + `billingOverview` | What needs attention today, then revenue — gross **and** net of refunds — and active subscriptions for a period, plus usage per meter. |
| **Payments** | `listPayments` | A page of payments, filterable by status and gateway, searchable by **your** reference or the gateway id — which charge failed, and when. Refund from here, and open one row in full. |
| **Customers** | `listCustomers` | The `billing_customers` mapping — which app user a `cus_…` belongs to, filterable by owner, gateway id and provider. Jump to a customer's payments or subscriptions. |
| **Subscriptions** | `listSubscriptions` | Who is `past_due` or `paused`, on which plan, with the trial and period end dates. Open one in full: its customer, the payments charged for it, the deliveries naming them, and what people did to it. |
| **Disputes** | `listDisputes` / `listDisputesDueWithin` | Every chargeback and pre-chargeback alert, and — the reason the screen exists — which evidence windows close next. Record how one ended from here. |
| **Webhook events** | `listWebhookEvents` | The ledger, defaulting to `failed`, filterable by event **type**, with each handler's error rendered in full. Retry from here. |
| **Activity** | `listAuditEvents` | Who refunded what, who closed which dispute, and every delivery this endpoint **refused**. |

### Linking to a screen

The screen you are on is in the URL fragment, so the back button works, a reload comes back to the
same place, and a view can be pasted into a ticket:

| Hash | Opens |
| --- | --- |
| `#/webhooks` | a screen, on its own default filter |
| `#/webhooks?status=failed` | a screen narrowed to a status — what the health panel's buttons write |
| `#/activity?status=webhook.rejected` | the activity screen narrowed to one action |
| `#/payments?customer=cus_9f2` | every payment recorded for one gateway customer |
| `#/payments/pay_8f2…` | the payments screen with that one payment open in full |
| `#/subscriptions?customer=cus_9f2` | every subscription of one gateway customer |
| `#/subscriptions/<id>` | the subscriptions screen with that one subscription open in full (its id or gateway id) |

It is a fragment rather than a path on purpose. The provider registers `<path>` as an **exact** route
and no catch-all — the prefix is shared with the package's own webhook endpoints — so
`<path>/webhooks` would be a 404 on reload. The fragment never reaches the server, and it works at
any mount `path` with nothing to configure. Anything it does not recognise opens the overview.

### The health panel

The first thing on the Overview, above the revenue tiles, is [`billingHealth`](/docs/payments/production#health-checks)
— the same six checks `node ace payments:health` runs, on the same thresholds:

- **Events claimed and never finished.** Nothing is consuming the dispatcher; the worker is not running.
- **Events the dispatcher gave up on.** Handlers threw and retries ran out, so those events never took effect.
- **Charges created that never confirmed.** What a webhook endpoint that stopped being reachable looks like from the inside.
- **Dispute windows closing.** An open chargeback whose evidence deadline is inside the next three days. The panel names each one — gateway, dispute id, how long is left — and its button opens the Disputes screen on exactly those rows.
- **Disputes still open and unanswered.** No deadline required, which is the point: most gateways publish none, and on those installs the check above reports zero forever. The panel names these too, oldest first.
- **Deliveries the endpoint refused, last 24 h.** A bad signature, an unparsable body, a provider nobody configured. Usually a rotated webhook secret that never reached the deployment — and invisible everywhere else, because a rejected delivery never becomes a ledger row.

Every one of these is a silent failure: the endpoints keep answering `200` while revenue quietly
stops landing. A healthy install shows one green line. An unhealthy one leads with the count, says
what it means, names which provider and event type is failing, and links straight to the rows.

<Callout title="Why health sits above revenue">
Revenue answers "how did we do". Health answers "is anything broken right now". On the morning the
worker is dead, the revenue tile still shows yesterday's healthy number.
</Callout>

### The two revenue tiles

Under the health panel the console shows revenue **twice**, because there are two true answers:

- **Revenue (gross)** — paid payments settled in the window, with refunds *not* subtracted.
- **Revenue (net)** — the same payments minus what went back (`amount - refunded_amount`).

A partial refund keeps its payment row `paid` at the full `amount` and records what came back
separately, so it moves the second tile and leaves the first alone. That is why both are on screen
and both say which one they are: for two releases the console showed only the gross figure under the
word "Revenue", and a charge that was half refunded was reported as fully earned with nothing
disagreeing. Both tiles are integer minor units formatted once, at render.

### Filtering by gateway

Every list filters by **provider** as well as status, and the list of providers comes from your own
data — not from the eighteen drivers this package ships. With Stripe and Pix in production, the
filter offers Stripe and Pix.

The store's list queries have no provider column filter, so the provider narrowing is applied over
pages read from the store, up to a bounded scan. When that scan stops short the console says so,
because "no Asaas failures" and "no Asaas failures in the rows I looked at" are different answers.
The Customers and Activity lists report no such caveat, and that is deliberate: every filter they
offer *is* a column the store applies, so there is no bounded scan behind them and claiming the
caveat would be claiming one that does not apply.

The webhook-event **type** filter is built the same way — `GET <path>/api/providers` reports the
event types this install has actually received, rather than the twenty this package can emit. A
filter offering twenty that return nothing hides the three that do not.

### Finding one payment

The question a console gets opened for is "did *this* person's payment land?", and the operator
holds one of three ids: the app's own reference for the order, the gateway's id for the payment, or
the gateway's id for the customer. The Payments screen has one search box that tries the app's
reference first and the gateway id second — an operator pasting from a support ticket does not know
which of the two they are holding.

All three lookups are **exact**. They are join keys, and letting `order-4` return `order-42` is a
wrong answer to a question about money.

Every payment row now carries the app's `externalReference`, the `refundedAmount`, and an **owner**.
A gateway customer nobody mapped reads as **unmapped**, not as a blank: it means charges are landing
that this console can never attribute to a person. The mapping is written by
[`ensureCustomer({ store, owner })`](/docs/payments/billing#reusing-a-gateway-customer) and by
nothing else.

### One payment in full

Clicking a row opens `GET <path>/api/payments/:gatewayId` — the current state, the owner, the
disputes filed against it, the ledger rows recorded for it, and who refunded it from this console.
The disputes are read with `listDisputes({ paymentGatewayId })`, so every dispute on the payment is
listed however many newer ones exist elsewhere; a custom store that ignores that filter still gets
the right rows, just from a page of the newest disputes overall.

<Callout type="warn" title="It is not a history, and it does not claim to be">
`billing_payments` is a single mutable row upserted in place. Its earlier states are recorded
nowhere, so "what changed on this payment, and when?" has no answer here.

The ledger strand lists the deliveries recorded for this payment: every ledger row keeps the
normalized `gatewayId` of the `payment.*` event it carried in `payment_gateway_id`, and the strand
is an indexed equality on it (`events.matchedBy: 'payment-gateway-id'`). Rows recorded before that
column existed have nothing to compare, so those alone are found by a `CAST(payload AS TEXT) LIKE`
scan of their stored payload — which can **over-match** a delivery that merely mentions the id. The
panel says so on screen.

No history table was invented for this: the strand is the ledger, read by payment.
</Callout>

The stored payload itself is still never returned. The timeline says an event arrived and what type
it was; what was inside it is [telescope's](/docs/payments/diagnostics) job.

### Money

Amounts are integer **minor units** everywhere — on the wire too — and the divisor is not always
100. The SPA renders with the currency's own exponent, the same table `src/money.ts` uses, so a
`¥1990` charge shows as ¥1,990 rather than ¥19.90 and a `KWD` amount keeps its three decimals.

### Disputes

A chargeback has a clock, and it is the only clock in this package that runs against you: every
network gives a fixed window to respond, and missing it loses the money **by default rather than on
the merits**. So the screen is two panels over the same table, in this order:

1. **Evidence windows closing** — the work list. Only the OPEN disputes that carry a deadline,
   soonest first, with the deadline as the leading column and a countdown in hours beside it
   (`in 5 hours`, not "today" — the difference is a morning). The horizon picker offers 24h, 3
   days, 7 days and 30 days, and opens on **3 days**, the same horizon `payments:health` alerts
   on. The count above the table is the list's `meta.total`, unbounded by the page.
2. **All disputes** — the log. Every dispute newest first, filterable by status (`warning`,
   `open`, `under_review`, then the resolutions) and by gateway.

The work list is deliberately **not** filterable by gateway. It is the one list whose whole job is
that nothing gets missed, and narrowing it to Stripe while an Asaas window shuts tonight is exactly
the failure it exists to prevent. Filter the log underneath; it is the same table.

Three things the rows are careful about:

- **A window that already shut still appears**, marked `past due` with how long ago. It is still
  open and still unanswered, and going quiet the moment it expires reads as resolved.
- **A dispute with no deadline is not in the work list at all**, and in the log its deadline cell
  says *the gateway sends no deadline* rather than showing a dash. `evidence_due_by` is null when
  the gateway told us nothing — several send no date, and Woovi's three-day rule is policy rather
  than a field — and "we were told nothing" is not "there is time".
- **A dispute can name no money.** Stripe's early fraud warning carries no amount, so the cell says
  so instead of rendering `R$ 0,00`, which would be a claim about an amount that does not exist.

`warning` is not a chargeback and does not look like one: nothing has been pulled back, a refund
now stops the debit from ever being filed, and the row says *no money moved* in words rather than
leaving that to a hue.

<Callout title="There is still no Fight button, on purpose">
No "fight this", no "accept", no "refund from the dispute". Not an unfinished screen — a decision.
Whether to submit evidence or simply refund turns on your margin, the customer's value, the dispute
fee, the evidence your app actually holds, and the chargeback ratio that puts a merchant into a card
network's monitoring programme — which is why refunding a dispute you would have won is sometimes
right. That decision belongs in your code, against your data, not behind a console button someone
can press without any of it. Submitting evidence is
[`submitDisputeEvidence`](/docs/payments/api-reference) on the driver.

The one action the screen *does* have — **Resolve** — is a different thing entirely: it records an
outcome that already happened at the bank. See below.
</Callout>

## Actions

Three things can be changed from the console. All are `POST` (a refund reachable by URL is a refund
a crawler can trigger) and all run through the same [`authorize`](#authorization) guard as every
read.

They also carry a CSRF token. `@adonisjs/shield` guards every state-changing route of the host app,
and the SPA sent none — so both POSTs were refused before they ever reached the console's own guard,
and the button did nothing with nothing on screen saying why. Shield publishes the token as an
`XSRF-TOKEN` cookie precisely so a browser client can echo it in `x-xsrf-token`, and the SPA now
does. No cookie means no header, which is the right answer for a host that does not run shield.
Reads are untouched: CSRF only guards mutations.

### Refund a payment

Offered on a `paid` row. The dialog restates the **amount** and the **customer** before doing
anything, takes an optional partial amount, and disables itself for the round-trip so a double click
is not a double refund. The refund goes through the driver that took the payment, resolved by name
from your `config/payments.ts`:

- A gateway with no refund API (Woovi/OpenPix) is refused **before** the call, with a sentence
  naming the gateway.
- A provider no longer in your config answers `503` with the manager's own message, which lists the
  providers that are configured.
- A gateway that refuses answers `502` carrying **its** message verbatim.

The local row is not rewritten. The gateway confirms a refund with a `payment.refunded` webhook, and
that is what moves the row to `refunded` — writing it optimistically would show a refund that may
never have settled.

A successful refund writes an **audit row** naming the person who made it, the amount asked for and
whether it was partial. The actor is your app's signed-in user (`ctx.auth.user`'s `email`, `name` or
`id`), `bearer` for a caller using a token, and `null` — "unattributed", never an invented "system" —
when the request carries neither.
A refund the gateway **refused** writes nothing: an audit of refunds that never happened is an audit
nobody can trust.

### Recording how a dispute ended

Several gateways publish no lost-dispute event at all. Asaas is one, and its driver hardcodes
`outcome: 'won'` when it closes a dispute — so a dispute that was **lost** sat at `open` forever,
the deadline check stayed red, and a fifteen-minute cron logged the same failure until nobody read
it, burying every other finding with it.

`POST <path>/api/disputes/:gatewayId/resolve` records the ending: a finished status, an outcome, a
note, and **who** said so.

```json
{ "status": "lost", "outcome": "lost", "note": "acquirer sided with the cardholder" }
```

`status` must be one of the finished dispute statuses — the full `DISPUTE_STATUSES` list minus the
open ones (`warning`, `open`, `under_review`). A "resolve" that could put a row back into `open` is
not a resolution, it is an edit box over a money table. `outcome` defaults to the status.

**Nothing is sent to a gateway.** The dialog says so twice: the decision was made at the bank, this
writes down which way it went. The write goes through `saveDispute`, whose absent-fields-are-left-
alone rule means the deadline and the reason the *opening* event carried survive it. It also writes
a `dispute.resolved` audit row — on a gateway that publishes no closing event, a human is the entire
provenance of that outcome.

### Retry a failed webhook event

The one thing that closes the loop after you fix a handler bug: a `failed` row means the effect that
event described never happened and nothing will retry it. Retry re-runs the event through the same
`WebhookProcessor` your app uses — built-in store sync **plus your own handlers**.

It is safe to repeat. The ledger re-claims a `failed` event and refuses an in-flight or already
processed one, which is the same guard that makes a gateway redelivery a no-op. A retry that went
through is recorded in [Activity](#activity--the-trail-nothing-else-keeps) as `webhook.retried`,
with who ran it.

**Every gateway replays, signed ones included.** The event is rebuilt from the ledger row's own two
columns — the raw `payload` and the `normalized` event recorded beside it — and handed straight to
the processor. No driver is involved and `parseWebhook` is never called again, so there is no
signature to re-verify from headers the ledger does not keep. Rebuilding through the driver would
make Stripe, Adyen and every other signing gateway answer `422`, leaving retry usable only on the
minority that do not sign.

<Callout type="warn" title="Events recorded before the `normalized` column existed">
`billing_webhook_events.normalized` arrived after the first release. There is nothing to run for
it — the library [owns its schema](/docs/payments/billing#the-billing-tables) and adds the column
on the next boot — but the rows already in the ledger are not backfilled, because the normalized
event was never stored to backfill from.

So a row older than the column has nothing to replay (the raw payload alone is not enough, and
rebuilding through `parseWebhook` would re-verify a signature computed from headers the ledger
never kept). Retry answers `422` saying so and leaves the ledger row exactly as it was, original
error and all. Redeliver those from the gateway's own dashboard; everything recorded since replays
normally.
</Callout>

## Configuration

```ts title="config/payments_dashboard.ts"
import { defineConfig } from '@adonis-agora/payments/dashboard'

export default defineConfig({
  // enabled: true,
  // path: '/payments',
  // currency: 'BRL',
  // authorize: (ctx) => ctx.auth.user?.isAdmin === true,
})
```

| Option | Default | Description |
| --- | --- | --- |
| `enabled` | `true` | When `false`, no routes are registered at all. |
| `path` | `'/payments'` | Route prefix. The HTML serves at the root; the JSON API at `<path>/api`. |
| `currency` | `'BRL'` | ISO 4217 code the money columns render in. Does not change what is stored. |
| `authorize` | open outside production, `403` in production | Who may open the console: an inline function, an authorizer class, or a lazy import of one. See [Authorization](#authorization). |
| `accessDenied` | the built-in page | What a browser sees when `authorize` refuses a page navigation. See [The access-denied page](#the-access-denied-page). |
| `viewer` | `ctx.auth.user` | `(ctx) => ({ label, email?, role? }) \| null`: who the sidebar footer shows as signed in. See [Signed-in user and sign-out](#signed-in-user-and-sign-out). |
| `signOut` | announced by authkit | The footer's sign-out: a POST action path, `{ href }` for a link, or `false` for none. |

### Authorization

The console has no login of its own. Operators sign in through your app, and `authorize` decides
who may open the console, returning `{ redirectTo: '/login' }` to send a signed-out visitor to your
sign-in page. When an API call answers `401`, the console UI follows its `redirectTo`, or reloads the
page so the server answers the navigation.

When `authorize` is omitted, the console is **open outside production** and **denies every request
in production** (`403`, pages and API alike). The app logs one warning at boot:

```txt
[@adonis-agora/payments] console has no `authorize` configured: it is open outside production and denies every request in production. Set `authorize` in config/payments_dashboard.ts.
```

`authorize` takes the same three forms as every Agora console. An inline function:

```ts title="config/payments_dashboard.ts"
export default defineConfig({
  authorize: async (ctx) => {
    if (!(await ctx.auth.check())) return { redirectTo: '/login' }
    return ctx.auth.user?.isAdmin === true
  },
})
```

A class, for an authorizer in its own file. It is built through the container, so `@inject()` works:

```ts title="app/policies/console_access.ts"
import { inject } from '@adonisjs/core'
import type { HttpContext } from '@adonisjs/core/http'
import type { ConsoleAuthorizer } from '@adonis-agora/payments/dashboard'
import AuditService from '#services/audit_service'

@inject()
export default class ConsoleAccess implements ConsoleAuthorizer {
  constructor(private audit: AuditService) {}

  async authorize(ctx: HttpContext) {
    const allowed = ctx.auth.user?.isAdmin === true
    await this.audit.record('payments-console', ctx.auth.user, allowed)
    return allowed
  }
}
```

```ts title="config/payments_dashboard.ts"
import ConsoleAccess from '#policies/console_access'

export default defineConfig({
  authorize: ConsoleAccess,
})
```

Or a lazy import of that class, so the config file does not load it at boot:

```ts title="config/payments_dashboard.ts"
export default defineConfig({
  authorize: () => import('#policies/console_access'),
})
```

Whatever the form, the answer is one of:

```ts
type ConsoleAuthorizeResult =
  | boolean
  | { allowed: true }
  | { allowed: false; reason?: 'unauthenticated' | 'forbidden' }
  | { redirectTo: string }
```

| The authorizer answers | Page | API |
| --- | --- | --- |
| `true` or `{ allowed: true }` | let through | let through |
| `{ allowed: false, reason: 'unauthenticated' }` | `401` page | `401` |
| `{ allowed: false, reason: 'forbidden' }`, `{ allowed: false }` or `false` | `403` page | `403` |
| `{ redirectTo: '/login' }` | `302` to that path | `401` with `redirectTo` |
| it throws | `403` page | `403` |
| it already answered (wrote a redirect) | that answer, untouched | that answer, untouched |

A denial is JSON for an API call (`{ "error": "forbidden" }` for a `403`,
`{ "error": "unauthenticated" }` for a `401`, plus `"redirectTo"` when the authorizer answered one),
the [access-denied page](#the-access-denied-page) with the matching status for a browser.

For machine access (a script, a health probe), `authorizeByToken` allows a request whose
`Authorization: Bearer <token>` header matches, compared in constant time, and answers `401`
otherwise. It reads the header only. An empty or missing token throws when the config loads:

```ts title="config/payments_dashboard.ts"
import env from '#start/env'
import { authorizeByToken, defineConfig } from '@adonis-agora/payments/dashboard'

export default defineConfig({
  authorize: authorizeByToken({ token: env.get('CONSOLE_TOKEN') }),
})
```

To let both operators and scripts in, pass both to `anyAuthorize`. It allows a request when any of
them does, tried in order (the first one that allows also decides the `tenants`):

```ts title="config/payments_dashboard.ts"
import env from '#start/env'
import { anyAuthorize, authorizeByToken, defineConfig } from '@adonis-agora/payments/dashboard'

export default defineConfig({
  authorize: anyAuthorize(
    authorizeByToken({ token: env.get('CONSOLE_TOKEN') }),
    (ctx) => ctx.auth.user?.isAdmin === true,
  ),
})
```


With [`@adonis-agora/authz`](/docs/authz) the shared helper reads your user and roles for you — the
same one every Agora console takes, so one RBAC gate reads identically across durable, telescope,
media, agent and payments:

```ts
import { authorizeByRoles } from '@adonis-agora/authz'

export default defineConfig({
  authorize: authorizeByRoles({ roles: ['ADMIN'] }),
})
```

<Callout type="warn" title="This console shows revenue — and can move it">
Payment amounts and customer ids are reachable through it, and the refund action moves money at your
gateway. Set `authorize` to a real guard before you deploy.
</Callout>

### Organizations

With tenancy on, `authorize` may also answer `{ allowed: true, tenants: '*' | string[] }`, and the
console shows each viewer only their organizations, with an Organization picker in the header. See
[Organizations](/docs/payments/organizations#the-console).

### The access-denied page

A refused **API** request gets JSON (`403 { "error": "forbidden" }`, `401 { "error": "unauthenticated" }`
when `authorize` said `reason: 'unauthenticated'`) — that is what the console's own `fetch` calls
expect. A refused **page** navigation — the console shell or its assets — gets a real page instead:
a dark card in the console's visual language showing the status, a sentence explaining the refusal,
a "Back to app" link and, when you set `loginHref`, a "Sign in" button. It carries
no inline script, so a nonce'd `script-src` CSP cannot break it (its one inline `<style>` picks up
`@adonisjs/shield`'s request nonce).

Tweak it with `accessDenied` — every field optional:

```ts title="config/payments_dashboard.ts"
export default defineConfig({
  accessDenied: {
    brand: 'Entre Textos',           // eyebrow + <title>; default "Payments"
    title: 'Sem acesso',             // default depends on the refusal
    message: 'Peça ao admin para liberar o console de pagamentos.',
    homeHref: '/admin',              // "Back to app"; default "/", `false` hides it
    homeLabel: 'Voltar',
    loginHref: '/entrar',            // your app's sign-in; default: no "Sign in" button
    loginLabel: 'Entrar',
    accent: '#f59e0b',               // any CSS colour; default: the console's cyan
  },
})
```

Or replace it. Pass a function and it receives the refusal (`status`, `reason` —
`'forbidden'` or `'unauthenticated'` — `basePath`, `loginHref`, and the CSP
`nonce` when there is one) plus the `HttpContext`. Return an HTML string to have it served with the
right status; answer the request yourself and return nothing to make the provider stand down:

```ts title="config/payments_dashboard.ts"
export default defineConfig({
  accessDenied: (info, ctx) => {
    if (info.reason === 'unauthenticated') {
      ctx.response.redirect(`/login?next=${encodeURIComponent(info.basePath)}`)
      return
    }
    return `<!doctype html><title>${info.status}</title><h1>Sem acesso</h1>`
  },
})
```

An `authorize` hook that already wrote a redirect still wins — the provider never overwrites a
`location` header, with or without `accessDenied`.

### Signed-in user and sign-out

The sidebar footer shows who is signed in, a light/dark toggle, and a sign-out button.

Without `viewer`, the console reads `ctx.auth.user` when the request is already authenticated: the
label is `fullName`, `name` or `email`, and the role is the first of `role` or `roles`. Pass
`viewer` to show something else, or return `null` to hide the user row:

```ts title="config/payments_dashboard.ts"
export default defineConfig({
  authorize: (ctx) => ctx.auth.user?.isAdmin === true,
  viewer: (ctx) => {
    const user = ctx.auth.user
    return user ? { label: user.fullName, email: user.email, role: 'billing' } : null
  },
  signOut: '/logout',
})
```

A string `signOut` is a path the button POSTs to, with the request's CSRF token as `_csrf` when
shield is installed. `{ href: '/bye' }` renders a link instead. Without `signOut`, the console uses
the sign-out that authkit's account console registers. `false` removes the button. Only
same-origin paths are accepted.

### Content Security Policy

The console works under a strict CSP. Everything it needs is same-origin: the bundle and the
stylesheet are served from `<path>/assets/`, the API is `<path>/api`, and the deployment config
(mount path, API base, currency, signed-in user, sign-out) reaches the page as a `<script type="application/json">`
**data block**, which is never executed and so cannot be refused. `script-src 'self'` is enough —
including [`@adonisjs/shield`](https://docs.adonisjs.com/guides/security/securing-ssr-applications)'s
`scriptSrc: ["'self'", '@nonce']`, the recommended setup.

The fonts (Sora and JetBrains Mono) ship inside the bundle and are served from `<path>/assets/`
too, so `font-src 'self'` covers them. `img-src` is never needed: the favicon is an inline `data:`
SVG, which `img-src 'self' data:` covers.

## The JSON API

The SPA is a client of a plain API, and so can you be — the same guard covers it:

| Route | Query / body | Returns |
| --- | --- | --- |
| `GET <path>/api/health` | — | the `billingHealth` checks plus the failure breakdown |
| `GET <path>/api/overview` | `period`, `from`, `to` | `billingOverview` metrics for the period |
| `GET <path>/api/payments` | `filter[status\|provider\|externalReference\|gatewayId\|customerId]`, `page`, `size` | a page of payments, newest first, each with `externalReference`, `refundedAmount` and an `owner` |
| `GET <path>/api/payments/:gatewayId` | — | one payment: current state, owner, disputes, ledger rows naming it (with `events.matchedBy`), and its audit rows |
| `GET <path>/api/customers` | `filter[provider\|ownerType\|ownerId\|gatewayId]`, `page`, `size` | a page of the owner mapping, newest first |
| `GET <path>/api/disputes` | `filter[status\|provider]`, `page`, `size` | a page of disputes, newest first |
| `GET <path>/api/disputes` | `filter[dueWithin]` (hours), `filter[provider]`, `page`, `size` | only the OPEN windows closing inside the horizon, soonest first |
| `GET <path>/api/subscriptions` | `filter[status\|provider\|customerId]`, `page`, `size` | a page of subscriptions, plus the whole-table `past_due` and `failing_renewals` counts |
| `GET <path>/api/subscriptions/:id` | — | one subscription, by its id or gateway id: current state, customer, the payments charged for it, the ledger rows naming them, and its audit rows |
| `GET <path>/api/webhook-events` | `filter[status\|provider\|type]`, `page`, `size` | a page of the ledger, newest first |
| `GET <path>/api/audit` | `filter[action\|actor\|provider\|subjectType\|subjectId]`, `page`, `size` | the audit trail, newest first, plus the action filter list |
| `GET <path>/api/providers` | — | the gateways **and the event types** present in your data |
| `POST <path>/api/payments/:gatewayId/refund` | `{ amount? }` | the gateway's refund; `amount` is integer minor units |
| `POST <path>/api/disputes/:gatewayId/resolve` | `{ status, outcome?, note? }` | the closed dispute plus the audit row; sends nothing to a gateway |
| `POST <path>/api/webhook-events/:gatewayEventId/retry` | — | `{ status: 'processed' }` plus the audit row |
| `GET <path>/api/consoles` | — | the other Agora consoles this viewer may open ([switcher](#switching-between-consoles)) |
| `GET <path>/api/consoles/search` | `q` | search across those consoles and this one |

The lists speak the [`@adonis-agora/filter`](/docs/filter) wire format:

```
GET /payments/api/payments?filter[status]=failed&filter[provider]=asaas&page=2&size=25
```

```json
{
  "data": [{ "gatewayId": "pay_123", "status": "failed", "amount": 19900, "...": "..." }],
  "meta": { "total": 120, "perPage": 25, "currentPage": 2, "lastPage": 5, "firstPage": 1 },
  "statuses": ["paid", "authorized", "pending", "failed", "refunded", "disputed", "canceled"],
  "currency": "BRL",
  "filters": { "externalReference": null, "gatewayId": null, "customerId": null }
}
```

- **Filters** are `filter[field]=value` (or `filter[field][equals]=value`), one exact value per
  field. A field the list does not have, another operator, or several values answer `400`.
- **Sort**: each list has one order — newest first (`sort=-createdAt`), or soonest deadline first
  (`sort=evidenceDueBy`) for the dispute work list. `sort` is optional; any other value answers `400`.
- **Paging**: `page` is 1-based, `size` defaults to 50 and is capped at 200. `meta.total` counts
  every matching row, not just the page.
- Endpoint-wide data sits beside `data`/`meta`: `statuses`, `currency`, `counts`, `actions`, and
  `filters` (the payment lookups echoed back, so the SPA can say "no payment carries reference X"
  rather than "no payments").

With the [filter client](/docs/filter):

```ts
import { filterQuery } from '@adonis-agora/filter-client'

const qs = filterQuery().where('status', 'failed').page(2, 25).toQueryString()
const res = await fetch(`/payments/api/payments?${qs}`)
const { data, meta } = await res.json()
```

`filter[dueWithin]` with no value uses the same 72-hour horizon `payments:health` alerts on, so the
console and the cron agree about "soon". A value that is not a whole, non-negative number of hours
answers `400`, and so does a `filter[status]` beside it — the work list is open disputes only.
`meta.total` is every closing window, so a full page still tells you how many more there are.

The action responses distinguish their failures rather than collapsing them into `500`: `404` for a
row that is not there, `409` for a row in the wrong state (a payment that is not `paid`, an event
that is not `failed`), `422` for an event with no stored normalized form to rebuild from, `502` for a gateway or handler
that refused, and `503` when the payments manager is not reachable at all.

When the billing layer is disabled (`billing.enabled: false`) the API answers `503` rather than
`500` — the store being absent is a deployment state, not a crash.

## Switching between consoles

When the app has other Agora consoles (durable, telescope, media, the agent console, the authkit
admin), the brand block at the top of the sidebar becomes a menu that links to them. It lists only the
consoles the current viewer may open: each one is asked through its own `authorize`. With no other
console, or none this viewer may open, the brand block stays as it is. There is nothing to configure.

<kbd>Ctrl</kbd>/<kbd>⌘</kbd> + <kbd>K</kbd> opens a search across those consoles. Here, a payment's
gateway id or your app's reference opens the payment, a customer's gateway id or owner id opens
their payments, and a subscription's gateway id or reference opens that subscription. With
organizations on, only rows of the organizations this viewer may see are found. The other consoles
answer with their own hits (runs, media records, users).

The menu runs the other consoles' `authorize` on each page load. If yours writes an audit trail,
skip it for these checks: the request carries `ctx.agoraProbe === true` while they run.

```ts title="app/policies/console_access.ts"
export default class ConsoleAccess {
  async authorize(ctx: HttpContext) {
    const allowed = ctx.auth.user?.isAdmin === true
    if (!(ctx as { agoraProbe?: boolean }).agoraProbe) await audit.record('console.open', ctx)
    return allowed
  }
}
```

A console your app mounts by itself can join the menu with `registerAgoraConsole` from a provider's
`boot()`:

```ts title="providers/reports_provider.ts"
import type { ApplicationService } from '@adonisjs/core/types'
import { registerAgoraConsole } from '@adonis-agora/payments/dashboard'

export default class ReportsProvider {
  constructor(protected app: ApplicationService) {}

  async boot() {
    await registerAgoraConsole(this.app.container, {
      id: 'reports',
      title: 'Reports',
      icon: 'generic',
      path: '/reports',
      order: 60,
      authorize: async (ctx) => ({ allowed: ctx.auth.user?.isAdmin === true }),
    })
  }
}
```

## MCP tools

When the app registers `@adonis-agora/agent/mcp_provider`, the console's data is also served to
coding agents (Claude Code, Cursor, Claude Desktop) on the app's dev MCP endpoint, `/mcp/agora`.
There is nothing to configure here: the tools follow this console's `authorize`, so whoever can open
the console can use them, and nobody else. With organizations on, they see the same organizations
the console shows them. A disabled console (`enabled: false`) serves no tools. The
[agent docs](/docs/agent/dev-tools) show how to connect a client.

```sh
claude mcp add --transport http agora http://localhost:3333/mcp/agora \
  --header "Authorization: Bearer $CONSOLE_TOKEN"
```

Reads are listed by default. They return what the console's JSON API returns, never a gateway
payload. Lists take `page` and `limit` (20 by default, at most 100) and answer `{ items, next, total }`.

| Tool | What it returns |
| --- | --- |
| `payments_get_overview` | Revenue, active subscriptions and usage for a `period` (or `from`/`to`). |
| `payments_get_health` | What needs attention: failed events, stuck payments, closing dispute windows, failing renewals. |
| `payments_list_payments` | Payments, newest first. Filters: `status`, `provider`, `reference`, `gatewayId`, `customerId`. |
| `payments_get_payment` | One payment with its owner, disputes, webhook events and audit rows. |
| `payments_list_subscriptions` | Subscriptions, plus the `past_due` and failing-renewal totals. Filter by `customerId`. |
| `payments_get_subscription` | One subscription (`id` or gateway id) with its customer, payments, webhook events and audit rows. |
| `payments_list_disputes` | Disputes; with `dueWithin` (hours), only the open windows closing soonest. |
| `payments_list_webhook_events` | The webhook ledger, with the error of each failed event. |
| `payments_list_customers` | The mapping from gateway customers to your app's owners. |
| `payments_list_audit` | The [activity trail](#activity--the-trail-nothing-else-keeps). |
| `payments_list_organizations` | With organizations on: the ones you may see. |

With organizations on, pass `tenant: '<organization id>'` to narrow a read to one of them, like the
console's Organization picker.

The three actions are hidden until the app opts in with `devTools: { actions: ['payments'] }` in
`config/mcp.ts`. Each is recorded in the activity trail with the actor `mcp:<caller>`.

| Action | What it does |
| --- | --- |
| `payments_refund_payment` | Refunds a paid payment, in full or `amount` (integer minor units). Moves money. Listed only when a configured gateway supports refunds. |
| `payments_retry_webhook_event` | Re-runs a failed webhook event through your handlers. |
| `payments_resolve_dispute` | Records how a dispute ended at the gateway (`status`, `outcome`, `note`). Sends nothing to the gateway. |

## Activity — the trail nothing else keeps

Four kinds of row, each of which is otherwise only a diagnostic — a log line, gone by the time
somebody asks:

| Action | Written when |
| --- | --- |
| `webhook.rejected` | the endpoint answered `400`. **The one that matters most**: a rejected delivery never becomes a ledger row, so a rotated webhook secret looks exactly like a quiet week while every refund, chargeback and dispute closure is dropped on the floor |
| `payment.refunded` | someone refunded from this console. The payment row moves only when the gateway's webhook lands, and that row names no person |
| `dispute.resolved` | someone closed a dispute the gateway will never close itself |
| `webhook.retried` | someone re-ran a failed webhook event, from this console or its MCP tools. The ledger row only says it is `processed` now |

`actor` is `null` when nothing authorised it in a human sense — a rejected delivery has none, and a
request with no signed-in user or token cannot name one. `null` means **unattributed**, never "the system".

`action` is a free string in the column, so an app recording its own actions with
`store.recordAuditEvent(...)` sees them here too; the filter list is a UI convenience, not a
validation whitelist.

<Callout title="An install that upgraded before running the schema">
`billing_audit_events` is a new **table**, so `CREATE TABLE IF NOT EXISTS` carries it to an existing
install exactly as well as to a fresh one — nothing from the post-ship `ALTER` phase is involved. An
app that upgrades the package before the table exists keeps working: every audit write is additional
to an action that already happened, so a missing table skips the note and answers `null` rather than
failing a refund the gateway already accepted. The screen is then simply empty.
</Callout>
