Federated console. An app that runs payments standalone (its own gateways, credentials, webhooks and billing store) can appear in another app's payments console, typically the Hub's: list it under `apps` in `config/payments_dashboard.ts` (`store: { connection, schema }`, `controlPlane: { connection, prefix }`, `actions`, `timeoutMs`) and the console reads its billing tables through a store that refuses every write, masking document numbers (`***.456.789-**`), reducing payment methods to brand + last 4 and dropping raw payloads, PIX codes and anything named like a credential. Every action (refund, cancel/resume/re-price a subscription, retry a webhook event, resolve a dispute, submit evidence) is a console command on the owning app's Redis (`<prefix>-payments-console`): exactly one instance claims it and runs it through its own console handlers, gateway and audit trail, with the Hub's viewer as the actor. The owning app opts in with `consoleCommands` in `config/payments.ts`, every action off unless listed in `consoleCommands.actions`; the console's `authorize` must also grant the viewer the action's capability (new `capabilities` field, e.g. `payments:refund`) and may limit the apps with a new `apps` field. Every federated action needs an `Idempotency-Key`: the owning app runs a key once and answers a retry with the first answer (Stripe also gets the key). New route `GET /api/apps`; every API route takes `?app=`. The console gets an App picker with a federated badge and notice, and disables the actions of a browse-only app.
