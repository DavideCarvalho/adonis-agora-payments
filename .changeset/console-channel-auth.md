'@adonis-agora/payments': minor

Security: federated console commands are authenticated, and webhook deliveries that gateways do not sign are confirmed with the gateway (reported privately).

Before, anything that could publish on the owning app's Redis could send a console command with any actor and any capabilities (`{"verb":"refund","capabilities":["*"]}` refunded through the gateway), and forge the answer.

**Breaking:** an app with `consoleCommands` and no way to authenticate the console now fails its boot (web environment), and so does a console with an `apps` entry it may act on and no way to authenticate (`actions: false` browses only). The ways, in order:

- **Together with `@adonis-agora/crypto`: nothing to configure.** When crypto is booted in the apps, commands are sealed with the `console-payments` key (was `payments-console`) of the owning app's crypto partition (`apps.<key>.partition`, default the key). The key is created where possible; otherwise the app logs the `crypto:keys:create` line. No grant on the owning app (a crypto server lets it decrypt its own `console-*` keys); a console that is a crypto tenant needs `crypto:seal:console-*`, and the crypto server creates a missing key on its first seal.
- **With authkit's calls between apps:** the console sends an app-call token for the owning app and the app verifies it with no configuration, combined with crypto when both are there. Without crypto, the app publishes its command public key in authkit's key directory (`console:payments`) and the console reads it there, so `controlPlane.publicKey` is no longer needed (an explicit one still wins). On a payments control plane, the app also accepts its own `controlPlane.verifyTenant`.
- **Explicit:** `crypto: { cipher, key?, owns? }` (any KMS), `token` + `publicKey` / `verifyTenant` (authkit or your own functions), or the same `secret` on both sides (no authkit, no crypto). Explicit options win; `crypto: false`, `token: false`, `verifyTenant: false` turn the detection off.

Every command must carry the viewer's capabilities (refused with `403`, code `capabilities-required`, without them). The console narrows what `authorize` returns to the payments console set (whole set when it returns none); `authorize` may also return `access: 'read'`, and a malformed `capabilities` now grants nothing (it used to be ignored). The console's actions on its OWN app now honor the same capabilities and `access: 'read'` (403 "the viewer lacks …"; every action stays open when `authorize` returns neither), and the page disables the buttons the viewer cannot use. A console token needs the console capabilities `payments:console:read`, `payments:console:write` or `payments:console:<action>` (`payments:refund` on a token no longer makes it a console). Viewers keep `payments:refund` and similar names. In every mode, commands older than a minute are refused, replays run once, and forged answers are ignored. Boot errors are a `ConsoleAuthConfigError` with the same wording as every Agora lib; the boot log names each side's mode (`crypto (auto, key console-payments)`, `token (…; sealed to APP_KEY)`, `secret`) and whether actions are on, and shows a public key only by a short id. `node ace agora:doctor` reports the mode on each side (`payments.console-commands`) and probes the crypto key (`payments.console-commands-key`, deep).

**Webhooks:** InfinitePay and Efí deliveries are now confirmed with the gateway before anything is recorded. The driver reads the payment back with its own credentials (InfinitePay `payment_check`, Efí `GET /v2/pix/:e2eid`) and builds the event from that answer. A forged or unconfirmed delivery is refused (400, no ledger row), so it can neither mark an order paid nor take the genuine delivery's event id. Both drivers now report `webhookVerification: 'confirmed'`, with nothing to configure. Mollie's classic flow (no `webhookSecret`) now trusts no body field either: a `tr_` id is read back as the payment and a `chb_` as `GET /payments/{paymentId}/chargebacks/{id}`, event and ledger id come from Mollie's answer, and an unsigned delivery for anything else, or one Mollie does not confirm, is refused (400, no ledger row). An unsigned body can no longer name the ledger id. It reports `'confirmed'` (was `'unsupported'`). Breaking only for code that calls InfinitePay's or Efí's `parseWebhook` directly: it is now async, calls the gateway, and throws on deliveries the gateway does not confirm.

Mercado Pago: its signature covers only `data.id`, the request id and `ts`, so nothing else in the body is believed. The ledger id is now built from the signed `data.id` and the fetched state (`mercadopago:payment:<id>:<status>:<status_detail>`, …), never the body's `id`, so a replayed signed request with a rewritten `id` lands on the same row; a `ts` more than 5 minutes off is refused; a chargeback's payment comes from the case lookup, not `data.payment_id` (a failed case lookup now answers 400 and is retried). Existing ledger rows: each event carries the old id in the new `WebhookEvent.legacyIds`, and the processor treats a row under it as a redelivery, through 1.x (removed in 2.0). Mercado Pago redeliveries are now fetched again before the ledger dedupes them. Subscription charges (`subscription_authorized_payment`) are now looked up and reported as the payment they made (with `subscriptionId`); every topic the driver does not look up is acknowledged with 200 and records nothing (it used to record an event typed from the unsigned `type`).

The control plane now checks that every subscription a card call names (`subscriptionGatewayIds[]`, `subscriptionGatewayId`) belongs to the calling app, and drivers encode gateway ids in REST paths. The card-tokenize limiter no longer counts refused attempts, prunes expired counters, and caps its memory.

Mixed Hubs (crypto apps and authkit-only apps behind one console) need no configuration: the console picks token or crypto per app at the first command (cached 5 minutes), a failed app-call token no longer blocks a crypto command, `APP_KEY` is also read from `config/encryption.ts` and the environment, and the key check uses crypto's `hasKey` (no failed-decrypt audit rows) when the server has it.
