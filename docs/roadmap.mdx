This page lists what the library does **not** do yet, and why each gap matters. Anything that
already works lives in the guides — start at [Providers](/docs/payments/providers) for the
per-gateway matrix.

## Gateways

- **The dashboard's webhook retry cannot replay a signed gateway.** The ledger stores the raw
  payload but neither the request headers nor the normalized event, and `parseWebhook` verifies a
  signature — so a Stripe or Adyen retry answers `422` and leaves the ledger row untouched, while
  unsigned gateways replay normally. Closing it means storing the normalized event alongside the
  raw payload in `billing_webhook_events`, which is a new nullable column and therefore a migration
  existing installs have to run. Worth doing: retrying a failed event after fixing a handler bug is
  the single most useful thing an operator can do, and today it works for a minority of gateways.
- **`MGA` has no right answer.** ISO 4217 gives the Malagasy ariary two decimal places (it is
  subdivided into five iraimbilanja, not a hundred), while Stripe treats it as zero-decimal. The
  exponent table follows ISO, so a Stripe charge in MGA will disagree with it. Nobody has hit this;
  it is written down so that whoever does finds the reason rather than a bug.

- **Pagar.me's `charge.chargedback` is deprecated.** Pagar.me's own event list says migrate to
  `chargeback.received` by **2026-09-30**. The driver maps the deprecated event to
  `payment.disputed` today; the replacement's payload shape is undocumented, and `data.id` there
  may be a chargeback id rather than a charge id — which would write a `disputed` row under an id
  nothing reconciles. This needs one real payload from a live account before the deadline. Until
  then the new event lands in the webhook ledger as an unknown type, which is visible rather than
  silent.
- **Asaas maps fewer payment statuses than Asaas has.** `RECEIVED_IN_CASH`, `REFUND_REQUESTED`,
  `REFUND_IN_PROGRESS`, `DUNNING_*` and `AWAITING_RISK_ANALYSIS` all fall through to `pending`.
  `RECEIVED_IN_CASH` is the one that matters: it is paid, and it reads as unpaid.
- **Batched webhook notifications.** `parseWebhook` returns a single event, while Adyen's
  `notificationItems` and Efí's Pix array can both carry several. Both drivers refuse a batch
  loudly rather than processing the first and dropping the rest, which is the safe half of the
  answer. The real fix is `WebhookEvent | WebhookEvent[]` on the contract with the dispatcher
  looping — Adyen documents one item per JSON webhook and Efí sends one in practice, so this has
  never fired, but "has never fired" is not "cannot".

- **The method a router routed.** `payments.driver('pix')` resolves the provider by method, but the
  method itself only reaches the driver when the charge also carries `method: 'pix'` — the manager
  hands back a driver, not a pre-configured one, so it has nothing to write the routed method onto.
  Every driver that varies by method (Stripe's `payment_method_types`, Asaas' and AbacatePay's
  `billingType`) reads it off the charge. Routing without it silently gets the gateway's default.
  Threading the routed method through the manager would fix it for all four at once.
- **Subscription amounts on Stripe.** `updateSubscription` takes an amount, a description and
  metadata. Asaas and AbacatePay apply the amount and the description; Stripe applies the
  description and metadata and drops the amount, because changing a price there needs the
  subscription item id and the shared input has no room for it. What is missing is a plan/price
  field on the input with proration handling. Woovi no longer fabricates a result here — it throws,
  because OpenPix subscriptions are immutable.
- **Outbound idempotency beyond charges.** Stripe now sends `Idempotency-Key` as a request option on
  `charge` and `createCheckout`, the two inputs that carry an `idempotencyKey`. `refund`,
  `createCustomer`, `createSubscription` and `updateSubscription` have no key in the shared
  contract at all, on any driver, so a retried subscription creation can still duplicate at the
  gateway. Adding one means every driver honoring it, not just Stripe — see
  [Idempotency](/docs/payments/concepts/idempotency).
- **A method on checkout and on subscriptions.** `CheckoutInput` has no `method`, so a Stripe
  checkout session is always created with the account's default methods.
  `CreateSubscriptionInput.method` exists and Stripe ignores it — a Stripe subscription bills
  whatever the Price and the customer's default payment method say.
- **Partial refunds on AbacatePay.** `refund()` accepts an amount and ignores it — every call is a
  full refund at the gateway.
- **More gateways.** Only Stripe, AbacatePay, Asaas and Woovi ship. The driver contract is the
  extension point in the meantime, and a driver you write is a first-class citizen of the router and
  the billing layer — see [Custom providers](/docs/payments/custom-providers).

## What the billing tables do not record

- **Partial refunds skew revenue.** A `payment.refunded` webhook overwrites the payment row's status
  with `refunded` and its amount with the refunded amount. `revenue()` sums rows with status `paid`,
  so a partially refunded charge leaves revenue entirely and its original amount is lost. The tables
  need a refunded amount and a partial state so the arithmetic can subtract instead of drop.
- **Splits are not attributed.** A split charge stores the full amount on one row; who received what
  is only in the gateway payload. Per-recipient reporting is on the app today — the manual pattern
  is in [Marketplace splits](/docs/payments/patterns/marketplace-splits).
- **Fiscal invoices are not persisted.** An emitted NFS-e is returned inline and never written
  anywhere, which is the root of the next section.

## Splits beyond Asaas

`split` sits on the shared charge input, but only the Asaas driver reads it. Stripe, AbacatePay and
Woovi ignore it silently — no error, no split. Woovi models recipients as subaccounts and the driver
can create, find and list them, but a charge cannot be pointed at one, so the subaccounts are
inert as far as the charge path is concerned. The point of a shared input is that a marketplace can
change gateways as a config change; today it cannot.

## Fiscal invoices

Invoice providers expose `emit` and `find`. Nothing in the library ever calls `find`, and there is
no `cancel`. NFS-e issuance is asynchronous at every provider — `emit` returns a pending note that
becomes issued (or rejected) minutes later — so an app has to poll the provider itself to learn the
outcome, with no place to store it. Three pieces are missing: persistence for emitted notes,
reconciliation of their status, and cancellation, which is a legal requirement rather than a nicety.
See [Invoices](/docs/payments/invoices).

## Billing layer

- **Auto-invoice the metered amount.** `meteredBill` and `meteredBillForSubscription` price a
  period's usage, and that is where it stops — nothing charges the overage or emits an invoice for
  it. The cron, the charge and the guard against billing a period twice are yours to write. See
  [Metered billing](/docs/payments/patterns/metered-billing).
- **A dashboard UI.** `billingOverview` is headless by design and returns aggregate metrics, but no
  UI ships with the package. See [Billing dashboard](/docs/payments/patterns/dashboard).

## Coverage

All four gateways now have a driver test suite that exercises the request bodies against a stubbed
gateway — Stripe's fakes the SDK client and asserts what reaches each call, including the request
options the idempotency key rides in. None of them touch a real gateway, so anything that depends on
account configuration (whether Pix and boleto are enabled on a Stripe account, for one) is
unverified here. The harness the suites use is documented in [Testing](/docs/payments/testing).

## Not planned

- **Refunds on Woovi.** OpenPix has no refund API. The driver throws a clear error and declares the
  missing capability so the router rejects the call before it reaches the network — that is the
  intended behavior, not a placeholder.
- **Subscription updates on Woovi.** Same shape: OpenPix subscriptions are immutable, so
  `updateSubscription` throws and tells you to cancel and recreate. It is not behind a finer-grained
  capability flag — `capabilities.subscriptions` stays `true` because Woovi does create and read
  subscriptions, and splitting the flag per operation would have to reach the webhook event
  filtering and every driver that declares it.
- **Gateway-specific features behind the shared contract.** Things only one gateway has (Woovi
  subaccounts, for instance) stay on the concrete driver class rather than being widened into the
  interface, so the shared contract keeps meaning the same thing everywhere.
