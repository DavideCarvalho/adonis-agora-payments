The dashboard mounts a billing console into your app: a React single-page app plus the JSON API it
runs on. It reads through the [billing store](/docs/payments/billing) — no gateway calls — so it
works offline from the gateways, answers instantly, and shows exactly what your database recorded.

```sh
node ace configure @adonis-agora/payments
```

`configure` registers `@adonis-agora/payments/dashboard_provider` in `adonisrc.ts` and publishes
`config/payments_dashboard.ts`. The provider registers the routes on boot — nothing else to wire,
and no extra package to install.

<Callout title="It mounts at /payments-dashboard, not /payments">
The payments provider already owns `POST /payments/webhook/:provider`. A console mounted over that
prefix would put its authorization guard in front of the gateway's delivery endpoint — which is how
a webhook ends up answering `403` to Stripe.
</Callout>

## What it shows

| Screen | Reads | What it answers |
| --- | --- | --- |
| **Overview** | `billingOverview` | Revenue and active subscriptions for a period, plus usage per meter. |
| **Payments** | `listPayments` | A page of payments, filterable by status — which charge failed, and when. |
| **Webhook events** | `listWebhookEvents` | The ledger, defaulting to `failed`, with each handler's error rendered in full. |

The webhook events screen is the one worth opening first after an incident: a `failed` row means a
handler threw and the dispatcher gave up, so whatever that event described never happened. The
`error` column is the only place that message survives.

Money is integer cents everywhere — on the wire too. The SPA formats at the edge with the `currency`
you configure.

## Configuration

```ts title="config/payments_dashboard.ts"
import { defineConfig } from '@adonis-agora/payments/dashboard'

export default defineConfig({
  // enabled: true,
  // path: '/payments-dashboard',
  // currency: 'BRL',
  // authorize: (ctx) => ctx.auth.user?.isAdmin === true,
})
```

| Option | Default | Description |
| --- | --- | --- |
| `enabled` | `true` | When `false`, no routes are registered at all. |
| `path` | `'/payments-dashboard'` | Route prefix. The HTML serves at the root; the JSON API at `<path>/api`. |
| `currency` | `'BRL'` | ISO 4217 code the money columns render in. Does not change what is stored. |
| `authorize` | see below | Per-request guard: `(ctx: HttpContext) => boolean \| Promise<boolean>`. |
| `dashboardAuth` | absent | Opt-in session layer on top of `authorize`. |

### Authorization

The default `authorize` is **open outside production**. In production it requires a bearer token
equal to `PAYMENTS_DASHBOARD_TOKEN`, compared in constant time, and **denies when the variable is
unset** — it fails closed. The token is read from an `Authorization: Bearer <token>` header, an
`x-payments-token` header, or a `?token=` query param.

Replace it with your own guard; a denied request gets a `403`:

```ts
export default defineConfig({
  authorize: async (ctx) => {
    await ctx.auth.check()
    return ctx.auth.user?.isAdmin === true
  },
})
```

With [`@adonis-agora/authz`](/docs/authz) the shared helper reads your user and roles for you — the
same one every Agora console takes, so one RBAC gate reads identically across durable, telescope,
media, agent and payments:

```ts
import { authorizeByRoles } from '@adonis-agora/authz'

export default defineConfig({
  authorize: authorizeByRoles({ roles: ['ADMIN'] }),
})
```

<Callout type="warn" title="This console shows revenue">
Payment amounts, customer ids and raw gateway payloads are all reachable through it. The default
token gate is a floor for staging, not an answer for production — put a real guard in front of it.
</Callout>

### A session instead of a token

`dashboardAuth` adds a signed session cookie on top of `authorize` (**both** must pass). It is
opt-in: omit it and there are no auth routes and no cookie. Two hooks, either or both:

- **`login`** — the console serves its own sign-in page at `<path>/login` and calls your hook to
  verify the credentials. The right shape when the console stands alone.
- **`session`** — your already-authenticated app calls the console's session endpoint, and your hook
  reads whatever you already trust to identify the operator. No second login.

```ts title="config/payments_dashboard.ts"
export default defineConfig({
  dashboardAuth: {
    secret: env.get('PAYMENTS_DASHBOARD_SECRET'), // HMAC-SHA256 key, 32+ bytes
    ttl: '8h',
    login: async (username, password) => {
      const user = await User.verifyCredentials(username, password).catch(() => null)
      if (!user?.isAdmin) return null // null denies
      return { id: String(user.id), name: user.fullName }
    },
  },
})
```

With a session configured, an unauthenticated page navigation is redirected (`302`) to the login
page and an unauthenticated API call gets `401`. `secret` is always required, plus at least one of
`login`/`session` — a `dashboardAuth` missing either fails at boot rather than serving an ungated
console.

## The JSON API

The SPA is a client of a plain API, and so can you be — the same guard covers it:

| Route | Query | Returns |
| --- | --- | --- |
| `GET <path>/api/overview` | `from`, `to` | `billingOverview` metrics for the period |
| `GET <path>/api/payments` | `status`, `limit`, `offset` | a page of payments, newest first |
| `GET <path>/api/webhook-events` | `status`, `limit`, `offset` | a page of the ledger, newest first |

Paging is clamped (50 by default, 200 maximum), so an unbounded `limit` from a query string cannot
select the whole table.

When the billing layer is disabled (`billing.enabled: false`) the API answers `503` rather than
`500` — the store being absent is a deployment state, not a crash.

## Without the console

Everything the dashboard renders is a plain function over the store, so a custom console, a Metabase
query or a Slack digest can read the same data without mounting anything. See
[Building your own](/docs/payments/patterns/dashboard).
