Everything in the quickstart runs against a sandbox with an in-process dispatcher. This page is the
gap between that and money moving.

## Set every webhook credential

This is the one that must not be skipped.

The library treats signature verification as **opt-in for the gateways where signing is optional**
(Asaas, AbacatePay, Woovi) so that local development works without configuring a dashboard. In
production that same leniency means an **unauthenticated endpoint**: anyone who can reach the URL
can POST a payload claiming a payment happened, and your handler will grant it.

```ts title="config/payments.ts"
providers: {
  asaas: payments.asaas({
    apiKey: env.get('ASAAS_API_KEY'),
    webhookToken: env.get('ASAAS_WEBHOOK_TOKEN'),        // ← not optional in production
  }),
  woovi: payments.woovi({
    appId: env.get('WOOVI_APP_ID'),
    webhookPublicKey: env.get('WOOVI_WEBHOOK_PUBLIC_KEY'),
  }),
  stripe: payments.stripe({
    apiKey: env.get('STRIPE_KEY'),
    webhookSecret: env.get('STRIPE_WEBHOOK_SECRET'),     // Stripe always requires it
  }),
}
```

Make them required in your env validation so a deploy without them fails at boot rather than at the
first forged callback:

```ts title="start/env.ts"
ASAAS_WEBHOOK_TOKEN: Env.schema.string(),
STRIPE_WEBHOOK_SECRET: Env.schema.string(),
```

For Woovi, prefer `webhookPublicKey` (RSA-SHA256) over the deprecated per-webhook HMAC. When both
are set the public key wins and the HMAC is ignored. See
[Webhooks → Validation](/docs/payments/webhooks#validation-per-provider).

## Turn off sandbox deliberately

`sandbox` on the Asaas drivers defaults to `NODE_ENV !== 'production'`. That is convenient and it is
implicit — a staging environment running with `NODE_ENV=production` talks to the **real** gateway.
Be explicit where it matters:

```ts
asaas: payments.asaas({
  apiKey: env.get('ASAAS_API_KEY'),
  sandbox: env.get('PAYMENTS_SANDBOX', false),
}),
```

Use different API keys per environment regardless. A sandbox key pointed at production fails loudly;
a production key pointed at staging charges real cards.

## Choose a dispatcher on purpose

`billing.dispatcher` decides how a validated webhook is processed:

| Value | Behaviour |
| --- | --- |
| `'auto'` (default) | durable when its provider is registered; else `@adonisjs/queue` when installed; else in-process |
| `'durable'` | a durable workflow run — **throws at boot when durable is missing** |
| `'queue'` | an `@adonisjs/queue` job — throws when the queue provider is missing |
| `'in-process'` | inline, with exponential-backoff retries in the background |

`'auto'` is the friendly default and it is also **silent**: an app that expected durable and forgot
to register its provider degrades to in-process and never says so. In production, name the backend
you actually run:

```ts title="config/payments.ts"
billing: { dispatcher: 'durable' }
```

Then a missing durable provider is a boot error, which is where you want to find out.

<Callout title="What in-process retries do and do not survive">
The in-process dispatcher retries in the background with exponential backoff — 5 attempts, 500 ms
base, capped at 30 s. That covers a transient database or gateway failure. It does **not** survive a
process restart: a deploy in the middle of the backoff window drops the pending retries. Durable
and queue backends do. Choose accordingly for money paths.
</Callout>

### Splitting api and worker

`billing.role` splits the deployment in two. The api half receives webhooks, validates and hands
them off; the worker half processes them:

```ts title="config/payments.ts — the api pods"
billing: { dispatcher: 'durable', role: 'api' }
```

```ts title="config/payments.ts — the worker pods"
billing: { dispatcher: 'durable', role: 'worker' }
```

A `'worker'` process does **not** mount `/payments/webhook/:provider` — it consumes what the api half
enqueued, so nothing can deliver to it directly. An `'api'` process skips resolving your handlers
entirely, since they run on the other side.

<Callout type="warn" title="Splitting needs a dispatcher with a channel">
`'in-process'` calls the processor inline: an `'api'` process would quietly process everything
itself and a `'worker'` would sit idle. `'auto'` can silently resolve to it. Both are refused at
boot when `role` is set, so a split deployment cannot come up half-wired:

```text
[payments] billing.role is "api", which splits receiving from processing — but
billing.dispatcher is "auto", which has no channel between the two halves.
Set dispatcher to "durable" or "queue", or drop billing.role.
```
</Callout>

Leaving `role` unset keeps one process doing both, which is the right shape until webhook volume or
deploy independence actually forces the split.

### The worker the dispatcher depends on

`'durable'` and `'queue'` move processing out of the web process, which means something has to be
consuming it:

```sh
node ace durable:work   # dispatcher: 'durable'
node ace queue:listen   # dispatcher: 'queue'
```

This is the deployment mistake that hides best: the webhook endpoint keeps answering `200`, the
ledger keeps filling up, and no handler ever runs. Add the worker to your process manager alongside
the web process, and alert on events that were claimed and never finished:

```sh
node ace payments:health
```

A non-zero **stuck** count means exactly that — something claimed the event and nothing consumed it.
See [Health checks](#health-checks) below.

## Respond fast

A webhook endpoint that holds the connection while a grant runs is a webhook endpoint that times
out, and a timeout means the gateway redelivers — which is safe, thanks to the
[ledger](/docs/payments/concepts/idempotency), but wasteful and slow to converge.

The handler's job is to **hand off**:

```ts
async handle(event: WebhookEvent) {
  await ProcessPaymentWorkflow.dispatch({ externalReference: ref }, { runId: `pay:${event.id}` })
}
```

Keep out of the handler: sending email, calling third-party APIs, generating PDFs, anything that
takes seconds. Those belong in the workflow or job the handler dispatches.

## Watch the right events

Every milestone is on the [diagnostics bus](/docs/payments/diagnostics), which is where alerting
belongs. Three are worth paging on:

```ts title="start/payments.ts"
import { onDiagnostic } from '@adonis-agora/diagnostics'

// A handler threw. The ledger says failed and the dispatcher is retrying.
onDiagnostic('payments', 'webhook.failed', ({ payload }) => {
  logger.error({ event: payload }, 'payments webhook failed')
})

// Payments failing in a cluster means a gateway incident, not a customer problem.
onDiagnostic('payments', 'payment.failed', ({ payload }) => {
  metrics.increment('payments.failed', { provider: payload.provider })
})
```

The signal that is hardest to see and most worth building: **charges created without a matching
confirmation**. A `charge.created` rate that stays healthy while `payment.succeeded` falls off a
cliff is a broken webhook endpoint, and nothing else in the system will tell you. Alert on the ratio,
not on either number.

## Health checks

Three failures in a billing install are silent — nothing throws, the endpoint keeps answering `200`,
and the first person to notice is a customer. `payments:health` asks about all three:

```sh
node ace payments:health
```

| Check | What a non-zero count means |
| --- | --- |
| **Stuck** — claimed over 15m ago, never finished | Nothing is consuming the dispatcher. The worker is not running. |
| **Failed** — dispatcher gave up, last 24h | Handlers threw and retries ran out; those events never took effect. |
| **Unconfirmed** — charges created over 2h ago, still pending | Charges are being created and never confirmed — a webhook endpoint that stopped being reachable. |

It exits **non-zero** when anything is wrong, so a cron entry or a container healthcheck can page on
it without parsing output. Thresholds are flags — `--stuck-after=5` (minutes),
`--unconfirmed-after=30` (minutes), `--window=48` (hours) — and `--json` prints the machine-readable
form for a metrics shipper:

```sh
node ace payments:health --window=48 --json
```

The same report is available in code, so a scheduled job can ship it wherever your alerts live:

```ts title="app/jobs/billing_health_job.ts"
import { inject } from '@adonisjs/core'
import { billingHealth, LucidBillingStore } from '@adonis-agora/payments'

@inject()
export default class BillingHealthJob {
  constructor(private store: LucidBillingStore) {}

  async handle() {
    const report = await billingHealth(this.store)
    if (report.healthy) return

    for (const check of report.checks.filter((check) => !check.healthy)) {
      logger.error({ check: check.key, count: check.count }, check.hint)
    }
    // report.failures groups the failed events by provider and type, worst first
  }
}
```

To read the failures themselves — the handler's error message survives nowhere else — page the
ledger:

```ts
const failures = await store.listWebhookEvents({ status: 'failed', limit: 20 })
// [{ gatewayEventId, provider, type, error, createdAt }, ...]
```

## Reconcile on a schedule

Webhooks are reliable, not infallible: an outage window, a dashboard edit, a gateway incident.
`payments:sync` pulls paid invoices back into the billing tables:

```sh
node ace payments:sync --all
```

Run it nightly. Remember what it does **not** do: it writes billing rows, it does not run your
handlers, so it will not grant anything. After a large reconcile, compare against your own tables —
or replay the events from the gateway dashboard so the normal path runs. See [CLI](/docs/payments/cli).

## Migrations and the ledger

The billing migrations create `billing_customers`, `billing_subscriptions`, `billing_payments`,
`billing_webhook_events` and `billing_usage_events`. `billing_webhook_events` is the one with an
operational profile: it grows with every event, forever, and it is what makes redeliveries safe.

Do not prune it aggressively. A gateway can redeliver an event days later, and a pruned id is an id
that will be processed a second time. Ninety days is a reasonable floor; longer if your gateway's
replay window is longer.

## Secrets

- **Gateway API keys** — full account access. Environment-injected, never in the repo, rotated on a
  schedule.
- **Webhook secrets** — whoever holds one can forge a confirmed payment. Same treatment.
- **Rotation** — most dashboards let you keep two signing secrets briefly. Roll them one at a time:
  add the new one, deploy, remove the old.

## Before you ship

- [ ] Every configured provider has its webhook credential set, and env validation requires it
- [ ] `sandbox` is explicit, and keys differ per environment
- [ ] Webhook endpoints registered in each dashboard (`node ace payments:webhook`)
- [ ] `billing.dispatcher` names the backend you actually run — not `'auto'`
- [ ] The matching worker is running (`durable:work` / `queue:listen`) if the dispatcher is not `in-process`
- [ ] If the deployment is split, `billing.role` is set per process and the dispatcher has a channel
- [ ] Migrations run; `billing_webhook_events` has a retention floor, not an aggressive prune
- [ ] Handlers dispatch rather than grant inline
- [ ] Every grant has an **inner** idempotency guard at the database
- [ ] Alerting on `webhook.failed`, and on the `charge.created` ÷ `payment.succeeded` ratio
- [ ] `payments:sync --all` scheduled
- [ ] Someone has watched an end-to-end payment succeed in production
